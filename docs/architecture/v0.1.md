# Architecture — Security Intelligence Platform v0.1

## 1. Objectif

La version v0.1 a pour objectif de construire la première chaîne
fonctionnelle de la plateforme de monitoring et de sécurité.

Le flux principal est :

Windows → Go Agent → Laravel API → PostgreSQL → Next.js Dashboard

Cette version doit permettre à un agent installé sur une machine Windows
de s'enregistrer auprès de la plateforme, d'envoyer régulièrement son
état et de transmettre des événements.

Le backend stocke ces informations et le frontend permet de les consulter.

## 2. Périmètre de v0.1

La version v0.1 comprend :

* un agent endpoint développé en Go ;
* une API backend développée avec Laravel ;
* une base de données PostgreSQL ;
* une interface web développée avec React / Next.js ;
* la communication sécurisée entre l'agent et l'API ;
* l'enregistrement des agents ;
* les heartbeats ;
* la collecte d'événements ;
* l'affichage des agents et événements dans le dashboard.

La version v0.1 ne comprend pas encore :

* Threat Intelligence ;
* Threat Hunting avancé ;
* Intelligence Artificielle ;
* détection comportementale avancée ;
* Kafka ;
* Redis ;
* Kubernetes ;
* haute disponibilité ;
* infrastructure multi-région.

Ces composants seront étudiés dans des phases ultérieures lorsqu'un besoin
réel apparaîtra.

## 4. Responsabilités

### Go Agent

L'agent est responsable de la collecte des informations et événements
nécessaires au monitoring de l'endpoint.

Responsabilités initiales :

* identifier la machine ;
* collecter le hostname ;
* collecter les informations du système ;
* communiquer avec l'API ;
* envoyer les heartbeats ;
* transmettre les événements.

### Laravel API

Laravel constitue le backend et le control plane de la plateforme.

Responsabilités initiales :

* exposer l'API ;
* authentifier les agents ;
* valider les données reçues ;
* normaliser les événements ;
* stocker les données ;
* fournir les données au frontend.

### PostgreSQL

PostgreSQL constitue le stockage principal de la plateforme.

Les premières données stockées sont :

* les agents ;
* les événements.

### Next.js Dashboard

Le frontend permet aux utilisateurs autorisés de consulter les données
collectées par la plateforme.

La première interface affichera :

* la liste des agents ;
* leur statut ;
* leur dernière activité ;
* les événements récents.

## 5. Flux principal

Le premier flux fonctionnel est :

```text
1. L'agent démarre
        ↓
2. L'agent collecte son identité
        ↓
3. L'agent s'enregistre auprès de Laravel
        ↓
4. Laravel valide l'enregistrement
        ↓
5. Laravel crée l'agent en base
        ↓
6. L'agent envoie régulièrement un heartbeat
        ↓
7. Laravel met à jour last_seen_at
        ↓
8. L'agent détecte un événement
        ↓
9. L'agent envoie l'événement
        ↓
10. Laravel valide et normalise l'événement
        ↓
11. PostgreSQL stocke l'événement
        ↓
12. Next.js récupère l'événement
        ↓
13. Le dashboard l'affiche
```

## 6. Pipeline backend

Les données reçues par l'API suivent le pipeline :

```text
RECEIVE
   ↓
AUTHENTICATE
   ↓
VALIDATE
   ↓
NORMALIZE
   ↓
STORE
```

Chaque étape devra être testée et sécurisée avant d'ajouter de nouvelles
capacités à la plateforme.

## 7. Principes de sécurité

La sécurité est considérée comme une fonctionnalité fondamentale de la
plateforme.

Les principes initiaux sont :

* authentification des agents ;
* autorisation ;
* validation des entrées ;
* chiffrement des communications ;
* gestion sécurisée des secrets ;
* principe du moindre privilège ;
* journalisation des actions importantes ;
* minimisation des données collectées ;
* contrôle humain des actions sensibles.

La plateforme doit éviter de collecter des données plus détaillées que
nécessaire pour l'objectif de sécurité défini.

## 8. Évolution prévue

La plateforme sera développée progressivement.

Les prochaines phases pourront introduire :

1. Event Pipeline avancé ;
2. Detection Engine ;
3. Alerts et Incidents ;
4. Threat Hunting ;
5. Threat Intelligence ;
6. AI Research Engine ;
7. AI Security Assistant ;
8. Scalabilité et haute disponibilité.

Les technologies supplémentaires ne seront introduites que lorsqu'elles
répondront à un besoin architectural identifié.
